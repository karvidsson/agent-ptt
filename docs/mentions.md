# Addressing agents with @mentions

Join a channel in the web UI, type `@`, and select an agent from the menu.
Send a request such as `@Finn please check the failing tests`. The message is
spoken normally and also queued for the selected agent session. Ordinary
channel chatter does not enter the agent's context.

## Setup

Restart the Agent PTT server to create the new inbox tables, then refresh the
plugins from your checkout:

```bash
python3 scripts/install_plugins.py
```

Restart your Claude Code or Codex session and trust the changed hooks when the
host asks. The receiving hook registers the session at its next prompt, tool
completion, or turn completion. Registered receivers appear in autocomplete.
The server's persistent session identity keeps the recipient stable across
rejoins and server restarts, even when its participation key changes.

The standalone hooks use Python's Unix file locking, matching the existing
macOS/Linux plugin workflow. Set `AGENT_PTT_RECEIVE=0` to disable receiving for
a session. This setting can also go in `~/.agent-ptt/announcer.env`.
Receiving is independent of the announcement toggle.

## When the agent receives a message

| State | Behavior |
|-------|----------|
| Working through tools | `PostToolUse` injects pending mentions into context; checks are throttled to once every two seconds per session. |
| Finishing its turn | A synchronous `Stop` hook supplies the messages as a continuation. |
| Starting a new turn | `UserPromptSubmit` supplies pending mentions with the new prompt. |
| Already idle or disconnected | Messages stay pending until another hook event runs, unless the agent keeps a waiter running: a loop on `GET /channels/{id}/inbox?wait=30` (the plugin's `ptt.py wait`, or `agent-ptt inbox --follow`, under Claude Code's Monitor tool) wakes the session per mention. |
| Idle for a long time | The server does not reap a receiving participant at the idle grace: it shows as `away` (reason `idle`) and keeps receiving mentions; any request brings it back. It is removed after `AGENT_PTT_AWAY_REAP_SECONDS` (default 7 days, `0` = never). |
| Session ended | The announcer's `SessionEnd` hook leaves the channel, which drops the receiver; new mentions of its handle in a project channel go to the project inbox instead. A resumed session registers again at its next hook event. |

Only the currently selected channel is checked. Switching away leaves the old
channel's messages pending until the session returns. A continued Stop hook
does not continue itself again; later mentions wait for a tool/prompt event
or a later normal turn. This bounds automatic continuation loops.

The UI shows a receipt per recipient:

- **Pending:** stored on the server, awaiting handoff.
- **Delivered:** the integration flushed the message to its hook host and
  acknowledged it. This is not confirmation that the model acted on it or
  finished the requested work.

Hooks fetch only a bounded pending inbox, not channel history. A per-session
file lock serializes overlapping hooks, and a local receipt journal retries
failed acknowledgements without injecting the same message again. A crash
between stdout handoff and journal persistence can still duplicate delivery;
message IDs accompany the context, and exactly-once task execution is not
guaranteed. Hook failures leave coding unaffected and undelivered requests
pending. The bridge for immediate delivery and idle wake-up is a later feature.

## Mention syntax and routing

- `@Finn` matches a complete receiver name, case-insensitively.
- Quote multi-word names: `@"Finn 2"`. Autocomplete does this automatically.
- Several mentions address several agents; repeating one creates one delivery.
- Emails, inline code, and fenced code blocks do not create text mentions.
- `@role:reviewer` and `@project` address a role or the whole project (role
  names are `[\w.-]+`, a trailing `.` is dropped); see below.
- Unknown or ambiguous names are rejected with `422` before the message is
  posted. The error lists the handles addressable in that channel (receivers,
  plus project members in a project channel) and says where `@role:<r>` and
  `@project` work. Autocomplete sends a stable recipient ID to disambiguate
  duplicate names.
- Autogenerated announcer messages explicitly disable routing, so quoting a
  user's request in an announcement does not create a feedback loop.
- The canned status responder defers messages with delivery records to the
  actual agent rather than answering the same request twice.

Only sessions registered with `receive_mentions: true` can receive. Human
participants and legacy announcement-only sessions do not appear in the
receiver menu. For external API clients, a channel participant exposes a
`mention_id` when receiving is enabled.

## Durable addressing in project channels

In a project's default channel (the project's `channel_id`, see
[projects.md](projects.md)), a mention does not need its target to be online:

| Mention | Goes to |
|---------|---------|
| `@Handle` of a receiving participant in the channel | its channel inbox (as above) |
| `@Handle` of a project member that is not a receiving participant (gone, reaped, or present without `receive_mentions`) | a work item to `agent:<member_id>` |
| `@role:<role>` | a work item to `role:<role>` (members who take the role later get it too) |
| `@project` | a work item to `project` |

Each queued work item is an `instruction` with `title` = the message's first
line, `body` = the message text and `context` = `{"channel_id", "message_id"}`;
it is idempotent per message and address. Its `from` is the project member
whose handle equals the sender's; when there is none the server creates one
(that handle, `harness` from the sender's session, mode `hooks`). Mentioning
yourself queues nothing. The channel message is posted (and spoken) as usual,
followed by the item's text-only notice (`Poppy → agent:Theo · instruction · …`).
The `say` response lists the items in `queued_items`; on the agent WebSocket
the sender gets a `{"type": "queued", "message_id", "queued_items"}` frame.

Outside project channels nothing changes, apart from the clearer `422`.

## API

Register a receiver with the usual join endpoint:

```json
{
  "handle": "Agent",
  "session_id": "stable-session-id",
  "agent": "Claude",
  "receive_mentions": true
}
```

The server still assigns its persistent session name and voice. The response
includes `key_id` and `mention_id`.

`POST /channels/{id}/say` and message frames on `/channels/{id}/ws` accept an
optional `recipient_ids` array:

- Omitted or `null`: resolve exact mentions in the text.
- Nonempty: address those receiver IDs and resolve other text mentions;
  explicit IDs disambiguate matching names.
- `[]`: post normally with mention routing disabled.

Recipients must be other receiving participants in that channel. At most 20
recipients and 8,000 characters are allowed for a routed message. Message and
delivery rows are committed together before broadcasting or queuing TTS.
Message/history responses include `deliveries`, each containing `recipient_id`,
`handle`, and `status` (`pending` or `delivered`).

| Endpoint | Request | Result |
|----------|---------|--------|
| `GET /channels/{id}/inbox?limit=6&wait=0` | `X-Participant-Key` header; limit 1–20; `wait` 0–60 s | Oldest pending messages; reading does not consume them. With `wait` > 0 and nothing pending, long-polls until a mention arrives or the wait ends. Every read is a sign of life. |
| `POST /channels/{id}/inbox/ack` | Same header; `{"message_ids": ["..."]}` (1–20 IDs) | Idempotent acknowledgement of this recipient's deliveries. |

Both endpoints also require the configured server API key, like other REST
routes. Hooks read `AGENT_PTT_API_KEY` from their environment or config file.
The participant key must belong to a receiver in the requested channel; an
acknowledgement cannot modify another receiver's delivery.

This uses the existing trusted-server/shared-key access model. It does not
implement the separate [organization authorization plan](archive/2026-09/org-auth.md).
Session IDs and display names are not authenticated organizational identities.
Relayed content is labelled as participant messages and preserves the agent's
existing permissions and task constraints.

## Storage

Two additive tables are created by `init_db()` without altering existing tables:

- `mention_receivers`: participation key → stable recipient ID and channel.
- `message_deliveries`: composite `(message_id, recipient_id)` key, channel,
  display name snapshot, creation time, and optional delivery time. A composite
  index supports pending inbox queries.

Deleting a channel removes its receiver bindings and delivery rows. Existing
messages are not retroactively converted to mentions.

## Verification

`tests/test_mentions.py` covers REST/WebSocket routing, restart/rejoin recovery,
transaction failures, receipts, and receiver/channel isolation.
`tests/test_receive.py` runs the hook against the test API, including stdout
handoff, acknowledgement retry, concurrency, throttling, and channel switching.

For a manual test, start a fresh agent session, post an explicit mention from
the UI while it is working, and observe pending → delivered followed by its
response. Repeat while it is idle: the receipt must remain pending until the
next prompt/tool/Stop event. Test on your installed host version; automated
tests verify the documented hook protocol rather than running a live LLM.

Hook protocol references: [Claude Code](https://code.claude.com/docs/en/hooks)
and [Codex](https://learn.chatgpt.com/docs/hooks).

## Connection policy

When an agent joins with `receive_mentions: true`, the server includes a
`mention_policy` object in the response (including repeat joins). Hosted agents
receive the same contract through authenticated `GET /api/workspace/me`.

```json
{
  "version": 1,
  "transport": "hooks",
  "tool_poll_interval_seconds": 2,
  "check_on": ["UserPromptSubmit", "PostToolUse", "Stop"],
  "idle_wakeup": false,
  "wait_supported": true,
  "wait_max_seconds": 60
}
```

`wait_supported` / `wait_max_seconds` advertise the inbox long-poll. They are
additive keys on version 1, so plugins that accept only version 1 with
`idle_wakeup: false` keep working; `idle_wakeup` stays false because the hooks
themselves still don't wake an idle session (a separate waiter does).

The receiver applies this policy and injects a brief connection notice once per
connection/policy into the agent's next prompt or tool hook. The notice explains
that the plugin checks mentions automatically, so the model should not start a
manual polling loop. Prompt and Stop checks bypass the tool throttle. An empty
Stop check never blocks completion merely to deliver a connection notice.

Version 1 accepts only hook delivery, the three supported events, no idle wakeup,
and a tool interval from 2 to 60 seconds. Unknown or malformed policies retain
the existing hook defaults. The plugin constructs the notice locally and does
not execute server-provided instructions, commands, or URLs. Existing servers
without this field remain compatible. `AGENT_PTT_RECEIVE=0` still disables all
receive work and notices.

This is event-based checking, not a background listener: an idle agent gets
queued mentions on its next hook event. Automatic idle responses still require
a supported host session-resume integration. No extra model calls or polling
processes are created. Server and plugin updates must both be loaded for this
contract to take effect; already connected local sessions pick it up on rejoin.
